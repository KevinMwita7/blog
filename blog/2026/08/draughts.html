Draughts, aka Checkers, Program

Introduction

One of the very first games I ever played was draughts, aka checkers. I remember drawing a draughts board in one of my books back in primary school and using pieces of paper as the men/kings. I still play it from time to time and it's the only game I currently have installed on my mobile phone. Never thought about doing my own implementation until I came to know of Arthur Samuel. He had the ingenious idea to teach computers how to play games and then use the observations to solve other problems. He ended up choosing draughts because it was simpler than chess, yet complicated enough to study how a computer could self learn and improve over time. This seemed like an interesting premise and I wanted to try and clone his original self-learning program. This post is a documentation of what I was able to achieve.

Reference code can be found on GitHub, glossary section is at the end of this article.

Quick Primer on Bitwise Operators

Bitwise operations will be used throughout the codebase to derive the game state. Below is a quick overview:

  • OR (|) - result is 1 if either or both bits is 1, 0 if both are 0
  • AND (&) - result is 1 if both bits are 1, 0 if either is 0
  • NOT (~) - flips bit to 1 if was 0 and to 0 if was 1
  • XOR (^) - stands for exclusive OR. Result is 1 when the bits differ and 0 when they're the same
  • Left Shift (<<) - shifts bits to the left by the specified step, pads right with zeros
  • Right Shift (>>) - shifts bits to the right by the specified step, pads left with zeros

Game Logic

For the computer to be able to play against itself and learn, it would need a game environment. This is what we'll be tackling in this section, starting with the game state.

Game State

Is modelled by position.h and position.cpp.

The instinctive way of representing a 2D board game is by using 2D arrays to model the rows and columns. This is a good enough approach, but not suitable for this case. The computer will need to play multiple games and perform multiple moves when searching for a best move. Iterating over the 2D array would be rather slow for this and therefore a better approach was warranted. My research online led to bitboards.

Bitboards use bits to represent positions on the board, with occupied cells being marked with 1 and empty cells with 0. A typical draughts board has 64 squares, however, a bitboard only needs 32 bits. This is because only the valid squares are considered in the implementation.

There'll be 4 bitboards to hold the pieces, 1 for each piece-kind (1 for black men, 1 for white men, 1 for black kings and 1 for white kings). Below is the state of the 4 bitboards at the start of the game:

These 4 boards are stored in position.h in the 2D array bb, with the rows representing Color and the columns PieceKinds. So bb[0] holds black pieces, bb[0][0] black men and bb[0][1] black kings. White pieces are bb[1], white men bb[1][0] and white kings [1][1].

The game state can then be derived by using bitwise operations, for example, all bitboards can be ORed to get the occupied squares i.e. BlackMen | BlackKings | WhiteMen | WhiteKings = occupied. Empty squares = ~occupied.

The game state uses transposition tables with zobrist hash as a played position cache. At the start of the game, the keys for each possible piece that could be on a square are initialized with random values, hence the 32 x 4 PIECE_KEY array (32 squares which might be occupied by any of the 4 color x piece combo). Additionally, a random value is also generated for the side key to keep track of which side made the move. To compute a position hash, first the side key is XORed into hash (only done if side to move is white since BLACK contributes 0 and XOR-ing on WHITE alone is enough to distinguish the two side-to-move states). Then for each occupied square, grab the random value that was generated at start of the game and XOR them to the hash too. The search result for that position is then stored into the transposition table with the computed hash as key. The underlying data structure that the transposition table uses is a vector. So given a hash, the destination index has to be derived.

To store an entry, the appropriate index has to be derived from the hash. The transposition table has an underlying vector with a size (n_entries) rounded up to the nearest power of two by std::bit_ceil. A mask is derived by subtracting 1 from n_entries. ANDing the hash with the mask is similar to hash % n_entries, which gives the appropriate index to use. This trick only works for powers of 2 because substracting one from a power of 2 results in a binary value with all bits on. Trying this on a non-power-of-2 won't have the same effect. When saving the entry, collision key has to be generated. This is done by right shifting the hash by 32 bits, thus discarding the lower 32 bits and leaving the upper 32 bits shifted down into the low half. The result is then truncated to 32 bits by static_cast<uint32_t>. The result will then be used as to identify collisions (different positions mapped to the same bucket). If the stored entry belongs to a different position (a true collision), it is always overwritten and if it belongs to the same position, it's only overwritten when the entry is from a different (older) generation or is not stored at a strictly greater depth than the new one.

Move Generation

Next is how moves are generated (modelled by movegen.h/movegen.cpp and position.h/position.cpp).

movegen.h declares the struct MoveList which will hold moves generated for a certain position. The struct contains the following properties and methods:

  • moves - an array that acts as the underlying container and has a maximum size of 64.
  • count - keeps track of elements in the moves array.
  • push - adds an element to the moves array and increments the count. See post-increment
  • clear - resets count to 0 effectively overwriting data on fresh pushes.
  • empty - checks if moves list is empty.
  • begin - returns pointer to first element in the moves array. Its const counterpart returns the constant to pointer variant that doesn't allow the data being pointed to being edit.
  • end - uses pointer arithmetic to return a pointer one past the last populated element in the moves list, matching standard C++ iterator convention. The const variant returns the constant to pointer equivalent.
  • operator[] - overrides the subscripting operator allowing MoveList[i] operations. The const counterpart doesn't allow updates of the memory location.

movegen.cpp defines a recursive static capture_from function that helps generate captures. It initializes the appropriate promotion back rank depending on the piece Color. It then uses the helper sq_bb function to create a bitboard with only the current piece populated. If the current piece isn't already a king and has reached promo rank, add that move to MoveList if there were any captures with promotion set to true and return since no further jump's available. capture_from then defines a try_jump lambda function that aids in finding and executing captures. It does the following:

  • returns if no enemy exists in adjacent squares.
  • returns if enemy exists in adjacent square but square where piece would land after jumping is not empty.
  • recursively attempt further captures, removing the jumped piece from enemy's bitboard (enemy & ~mid_bb), updating empty_bb to include the vacated origin/mid squares (excluding the new landing square) and updating the captured pieces bitboard.
If piece is king or is black: generate middle square to jump and square to land for both diagonally upper left and right squares and attempt the jump (and vice versa for white pieces). Finally, the base condition adds the move to list if no continuation exists and there is a capture.

generate_captures function searches the game for any available captures. It initializes the current player's Color and the enemy, empty and current player's piece bitboards. While there are still men on the current player's bitboard, take next man and generate captures for them using capture_from. It then gets the current player's king bitboard and generates captures for it too.

generate_quiets function looks for moves that don't result in a capture. It first initializes the current player Color and the men, kings, empty squares and promo rank bitboards. It then declares the FwdFn alias that takes in a bitboard and returns a square. Additionally, it declares the emit lambda function that populates the MoveList with possible destination squares. If current side is black then call emit twice:

  • first call passes in the first argument as the bitboard with valid destinations obtained by shifting the pieces up diagonally then ANDing with empty squares. The second argument is true since the pieces are men and third argument defines the FwdFn function that reverses the move and then returns the original square the subject piece occupied. The second call to emit gets valid diagonally up left destinations for the men.
  • above is done but in reverse for white men.
  • quiet moves in all diagonal directions are then generated for all Kings.

generate_moves then prioritizes captures if any, else, generate quiets.

has_legal_moves is used to determine if a Position has any valid moves. It returns true if there are any valid jumps as determined by the helper has_captures function (checks to see if a piece has an enemy it can jump over and whether it'll land on a valid square if it does). If no jumps exist, it checks whether there any valid neighbouring squares it can move to.

Once a move has been generated, they can then be passed to do_move in Position for execution. To execute the move, the current Color's turn is first determined (the opponent will be the opposite). Then the PieceKind is determined by checking whether it's in the kings bitboard or not. The number of previous moves without a capture is recorded and the captured kings bitboard (useful when updating the zobrist hash) is extracted. The zobrist hash is then updated by XORing the current piece's key into it. Additionally, the zobrist hash is updated with the keys of the captured pieces by looping through the captured pieces bitboards and XORing the keys into the hash. Then, the key of the piece's final destination is XORed in, using KING instead of the original kind if the move was a promotion. Then the current side's turn key is XORed into the zobrist hash. Next comes the board updates. The from square bitboard is ORed with destination square bitboard and the result XORed with the current players bitboard. This removes the piece from the origin square and places it on the target square. Then, the opponent's captured bitboard is NOTed and the result ANDed with their current men bitboard resulting in only the non-captured bitboards remaining on the game. The same is repeated with the opponent's captured bitboard and their current kings bitboard to updated the opponent's kings bitboard. These two operations are safe to perform simultaneously because any given captured square belongs to exactly one of the opponent's two piece bitboards (a square can't simultaneously hold an enemy man and an enemy king). If the piece got promoted, remove it from the piece's bitboard by negating said bitboard and ANDing the result with the men bitboard. OR the sole moving piece bitboard into kings bitboard to update the current player's kings bitboard. The occupied squares bitboard is updated by ORing all the four piece bitboards together (black men | black kings | white men | white kings), and then NOT the result to get the non-occupied squares. The side_to_move is updated to the opponent as its now their turn, the ply incremented and reversible reset if there was captured or incremented if none.

Undoing a move is basically the reverse. The current player and the opponent are the opposite of what they were when move was executed. The current PieceKind after move was made is a king if the move was a promotion, else, the it's a king if it's was in the previous side_to_move king bitboard and a man otherwise. The original PieceKind before a move was made is determined to be a man if said move was a promotion, and the current PieceKind if not. The hash is then reversed to state before move was performed by XORing it with the key piece key in destination square (opposite of from square in do_move). Captured pieces bitboard from the move to reverse are retrieved and for each piece in the bitboard, extract it, determine its kind by checking if it's in the captured kings bitboard or not and then XORing the piece with the hash to restore the hash before the piece was captured. Hash is then XORed with the piece's original square and then the SIDE_KEY, resetting it to original state before move. Piece is removed from the king board and placed onto the men's bitboard if the move resulted in promotion. The destination square and from square bitboards are ORed together, resulting in a bitboard with both from and to square populated. This bitboard is then XORed with the mover's bitboard, leading to only the from square persisting in the mover's bitboard. Captured kings bitboard is then ORed with the opponent's kings bitboard, undoing bb[them][KING] &= ~m.captured from do_move, leading to any captured kings being restored. Captured men are obtained by ANDing all captured pieces board with the complement of the captured kings board i.e. captured pieces with kings excluded. Result is then ORed into the opponents board, restoring the original state before capture. Currently occupied squares are constructed by ORing the men and kings bitboard of all Colors. Empty squares will then be result of ~occupied. Side to move is set to previous move's Color, ply decremented and reversible count set to count before move.

Position Notation

The game needs a way to record the game state i.e. piece positions and moves. Enter Portable Draughts Notation. From the notation, it's possible to know whose turn it is, the piece positions on the board and the executed moves. Take for example the PDN below: 

[Event "Endgame Study"]
[Black "A. Player"]
[White "B. Player"]
[SetUp "1"]
[FEN "W:W18,22,25,29,K31:B6,10,K13,K17,21"]
[Result "*"]

1. 31-27 17x26 2. 25-22 26x17 3. 18-14 *

The above notation's header can then be interpreted as:

  • [Event "Endgame Study"] - the name of the match/event.
  • [Black "A. Player"] - the player with the black pieces in last-name first-name format.
  • [White "B. Player"] - ditto for white.
  • [SetUp "1"] - indicates FEN is used.
  • Current board position W:W18,22,25,29,K31:B6,10,K13,K17,21 - the W at the start means it's White's turn, the colon separates the side_to_move from the positions. Then the W indicates all pieces that follow until the next colon are white. The 'K' before a piece indicates that the subject is a King. Same goes for black pieces after the 2nd colon.
  • [Result "*"] - outcome of the event. 1-0 if White (or first-named side) won, 0-1 if Black won, 1/2-1/2 is a draw and * is unknown/ongoing/not recorded

Then the moves executed so far follow. In this case, the moves are: 1. 31-27 17x26 2. 25-22 26x17 3. 18-14 *. The moves are numbered from 1., the '-' represents a quiet move from original to destination square with no jumps, the 'x' represents a move with a jump (17x26 is Black jumping White's man on 22, landing on 26) and the trailing '*' the trailing * closes the movetext and marks the result as unknown/ongoing, mirroring the [Result "*"] tag. It's the same token that would be 1-0, 0-1, or 1/2-1/2 if the game had concluded.

notation.h/notation.cpp are responsible for PDN serialization and deserialization of moves and positions. The engine uses parts of the PDN (the FEN-style position string and the bare move tokens) in conjuction with the UCI (discussed in the protocol section) to implement behaviour.

The functions below are responbile for everything PDN related:

  • parse_pdn_position - builds a Position from a FEN-styled position string. It extracts the side_to_move first and then the pieces, populating them in the relevant of the 4 bitboards.
  • to_pdn_position - constructs a FEN-styled position string from a Position. It first appends the side_to_move and then a colon, then 'W' to indicate white pieces follow, the White pieces bitboards (kings then men) follow, colon delimiter is appended next, then 'B' to indicate black pieces follow and finally the Black pieces (kings followed by men).
  • parse_move - given a move string, it builds a Move, searches the position's generated legal-move list for a from/to match and returns the resulting Move. It scans the whole string and collects every run of digits into an array, and then takes the first number as from and the last number as to ignoring whatever's in between. That matters for multi-jump captures like 1x10x19: the intermediate landing square 10 is read but thrown away and only 1 → 19 is used to match against the generated move list. It then checks whether the generated move exists for the associated position, returning it if so, and NULL_MOVE otherwise. This works because generate_moves already produces a single Move object per full jump sequence (from/to/captured-mask). Therefore, the parser doesn't need the intermediate squares, it just needs endpoints.
  • move_to_string - makes a move string from a Move. Moves are 1-indexed, so 1 has to be added to the move indexes.
  • parse_pdn - parses the entire game moves list using the parse_move function, advancing the Position move-by-move so each subsequent parse_move call resolves against the correct board state.

Performance Test

In draughts, the node counts for standard starting positions at each depth are already known. Therefore comparing the engine's output against them catches move-generation bugs (missing captures, wrong mandatory-capture handling, bad king move logic, illegal moves slipping through, etc). This can be achieved via perft, a function that counts and reports the leaf nodes at a certain depth, which can then be compared to the published references for bug detection. Perft originated from chess developmenet and traditionally served as a move-generator speed benchmark and a correctness check but this engine only uses it for the latter.

perft.h/perft.cpp are responsible for this in this implementation. perft does a depth-first walk of the move tree, playing each legal move and counting the nodes at each level recursively until it reaches the leaf. It then walks back up the tree, summing the leaf counts at each depth, and undoes the performed move. perft_divide does the same but reports the count per root move in addition to the total. Once the node count for a particular depth have been generated, the developer or unit tests can compare this with the known correct values. This is exactly what test/perft.cpp does:

  • There is a test case for depths 0, 1, 2 and 3 and the result compared against their known node counts i.e. perft(start_position, 0) == 1, perft(start_position, 1) == 7, depth 2 == 49, depth 3 == 302. These match the standard published perft sequence for draughts (7, 49, 302, 1469, …), so any move-generation regression that shifts these numbers fails the test immediately.
  • Targeted edge cases beyond raw counts: a terminal position (no pieces for the side to move) returns 0 at any depth, a forced-capture position returns exactly 1 leaf at depth 1 and 0 at depth 2 (verifying mandatory captures are enforced, not just counted).
  • Non-mutation check: a full test (DoesNotMutatePosition) asserts every field of Position is bit-identical before and after a depth-3 perft run, guarding the do_move/undo_move symmetry perft relies on.
  • perft_divide gets its own suite: total matches plain perft, one output line per root move, correct -/x separator per move type, and the same non-mutation guarantee.

Best Move

To win the game, the engine has to be able to execute the best move. The popular algorithm used to find such a move is the minimax algorithm. It takes advantage of the fact that draughts is a zero sum game whereby one side's gain is the other side's loss. Therefore, minimax picks the maximum score at the maximizing nodes and the minimum score at the minimum nodes. This is because maximizing nodes represent the player's turns while minimizing nodes represents the opponent's turn. The maximizing and minimizing nodes alternate at each depth, starting with maximizing node at the root. However, this introduces complexity since whether the type is maximizing or minimizing has to be tracked at each level. Keeping track of the node type can be neutralized by using negamax.

Negamax picks the negative of the maximum score at a node. This is because the score of a player at a node favours that player as much as it punishes the opponent. Allegorically, picture the score of a basketball game not as two separate scores, but as a single running margin: my points minus yours. When I hit a 3-pointer, my margin goes up by 3. But watch that same shot from your side of the court, your margin (your points minus mine) just went down by 3. Same shot, opposite sign, depending on whose scoreboard you're reading. That's the whole trick behind negamax. Instead of one player maximizing "my score" and the other minimizing "their score," everyone just maximizes their own margin. The catch is when it's my turn and I want to use the margin my opponent already figured out for their next move, I have to flip its sign first, since their +3 is my -3. That flip is the only extra step negamax needs; otherwise both players run the exact same "maximize my margin" logic.

The searching algorithm needs a way to know whether searching a certain branch might result in a better move, or if said branch can be safely ignored. That's where alpha beta pruning comes in. The name is derived from the two variables used to keep track of the scores. Alpha keeps track of the minimum score that the maximizing player is assured of, and beta, the maximum score that the minimizing player is assured of. Negamax flips alpha and beta at each level because the maximizing and minimizing players alternate at each depth, and breaks the moment alpha >= beta. This is because beta was handed down from the parent node as the best result the opponent can already lock in elsewhere, before even considering this branch. If any move here scores >= beta, then playing into said position would hand the opponent a worse outcome than a better one they can already guarantee themselves elsewhere. So the opponent, one level up, would simply never choose the move that leads into this node to begin with, meaning the rest of this node's sibling moves are irrelevant to search further, since the parent's decision is already settled regardless of what they'd turn out to be. From a human's perspective and not the engine's, alpha >= beta means that the current move being considered is not necessarily the best move, but would hurt the opponent enough that there's no need searching any further. The opponent would see this too and try avoiding making their move that would enable this damaging move to take place in the first place. The engine's main assumption here is that the players will always make the best move, which is not always the case.

Another thing to consider when searching for the best move is draw detection. A game is considered a draw under 2 conditions:

  • the number of plies with no captures since start of position till current ply exceeds threshold - the count of moves without a capture gets incremented each time there is no capture, and if the count exceeds the tolerable limit a score of zero gets returned to indicate a draw. However, the count gets reset whenever a capture is found and the whole process gets repeated again until either a draw is found, a good move is found or time runs out.
  • sequence of moves lead to a position getting encountered at least twice since the start of the game - multiple move sequences result in the same position been encountered at least twice. This doesn't necessarily mean that a move was played more than twice, but rather, multiple sequence of events led to same resulting position, which is indicative of a draw.

The final piece of the search algorithm is the iterative deepening search. What this means is that the algorithm searches all nodes at depth d, before proceeding to d+1, then d+2, ... d+n. It only reports the result of a depth d if it was able to complete searching at that level without interruption. Otherwise, it returns the result from the previous, fully-completed iteration (one depth shallower) since that was the last fully searched depth. Finally, the maximum allowed depth is set to 64 as a means of capping unbounded growth.

Protocol

Now that the game components exist, the next thing on the list is making them work together. This is handled by protocol.h/protocol.cpp an implementation of the, Universal Chess Interface. Below are the commands used to run the game:

  • quit/exit - stop searching and break the game loop, effectively murking it.
  • ucinewgame - stop searching and reset game position, search parameters and history to original state.
  • isready - just prints out readyok for now, but should canonically sync game state.
  • setoption - used to change internal parameters of the game. This engine just ignores it.
  • position - parses and creates a Position from the PDN string. If the PDN string is followed by the moves subcommand, the included moves get executed as well, with checks for draws being conducted after each move.
  • move - executes the specified move and checks for a draw afterwards i.e. 40 or more successive plies with no captures or position appears at least thrice in game history.
  • stop - abandon searching for position but game stays alive. Not to be confused with quit/exit.
  • go - informs engine to start the calculations. Allows the subcommands depth, movetime and ponder. The depth subcommand set the upper limit of how deep a search tree can grow, and ponder instructs the engine that there is no search time limit, but the depth is limited to 64 to avoid stack overflows. movetime is the time limit set for a search. It gets applied immediately if the ponder subcommand was not issued and applied after a hit if search was in ponder mode.
  • ponderhit - issued if player does a predicted move. The entire sequence of events is: the caller predicts an opponent's move, sets the position to what the board would look like after that move, and sends 'go ponder' command. As the opponent is thinking, the search keeps running deeper and deeper on the predicted position. Once the opponent makes their move and that move was the predicted one, the caller issues the 'ponderhit' command and the game continues searching but now with the time limit, if any was specified. However, if the player doesn't play the predicted move, the caller sends 'stop' (killing that now-useless search), sets the position to the real resulting board, and issues a fresh go with the real time budget, starting from scratch, since the prediction was wrong.
  • perft - see here.
  • moves - generates and prints moves for current position, but doesn't execute them.
  • d - prints the board snapshot.
  • any other command falls to final conditional branch, which then logs an error.

The game is multithreaded when running a non-browser environment, with the game loop executing in the main thread and the search happening in the background thread. Naturally, this comes with the concern of race conditions. The first affected area is the out stream because two commands may try to write to the out stream at the same time. To counter this, a mutex is introduced, and the writing threads first have to acquire a lock on the mutex before writing out. Decided to use lock_guards because they release resources automatically whenever they go out of scope, significantly simplifying threads management.

The second area is signalling the search thread to stop a search. It happens a whole lot throughout the code, therefore warranting the creation of the stop_search helper function in protocol.cpp. stop_search first sets the stop_flag_ atomic boolean to true, signalling any running search to stop, then joins the search thread if it's joinable (not detached/disposed), blocking until the stale thread actually stops, and finally resets stop_flag_ back to false for the next search. This helper is called by stop/quit/exit/ucinewgame/go, basically any command that needs the searching thread stopped before doing its own thing. In the 'go' command,
search_thread_ = std::thread(run_search) spins up a new thread running the run_search lambda and stores its handle in search_thread_ for these future interactions. For a plain go, that thread is joined immediately and handle_command blocks until run_search finishes, so the caller sees bestmove before the next command is read. The thread only keeps running past handle_command's return during go ponder. run_search captures a copy of the history and passes it to the search algorithm, making search aware on any moves made earlier during the course of the game.

Sidenote, peep the memory_order_relaxed argument passed when setting the stop_flag_ atomic variable. It essentially means that no synchronization (no locks) is used when updating the variable but atomicity is guaranteed (the operation of setting a variable may seem as one at code level but CPU execs it in multiple steps. Atomicity means all these steps either succeed or none of them happen). Contrast this with ponder_switch_ms_, used for ponderhit. That one is set with memory_order_release on the main thread and read with memory_order_acquire on the search thread. The difference is that ponder_switch_ms_ carries a value (the real time budget) that the search thread needs to actually use once it observes the switch, not just a true/false signal. Release/acquire guarantees that everything written on the main thread before the store, pending_go_params_'s real time getting set in this case, is visible to the search thread after it does the acquire-load. Relaxed wouldn't give that guarantee.

However, when in a browser environment, the game runs in a single thread due to JavaScript's event loop. Therefore, the go command checks if the __EMSCRIPTEN__ macro is defined, indicating that the code is running as Web Assembly module. If so, run_search gets called without spawning a thread.

GUI

To allow human players to play, a graphical board is needed. For this, the browser is a perfect medium because of HTML's simplicity. C++ can run in a browser as a WASM module, making its commands accessible to programs that want to interface with it. This is where emscripten comes into play. It's what will be used to compile the code into a WASM runtime. Emscripten provides the option of providing a shell HTML file to which the compiled WASM gets outputted. Since the project uses CMake as its build tool, the shell-file option was passed in the target_link_options in the project's CMakeLists.txt. This means that whenever someone selects the wasm-debug preset and then builds the project, an HTML file gets generated with the draughts engine attached as a WASM module. If using Visual Studio, this is as easy as selecting WebAssembly Debug from the configurations dropdown and running the project.

Taking a closer look at the project's CMakeLists, you'll notice the command option
"-sEXPORTED_RUNTIME_METHODS=['ccall','cwrap']". This instructs emscripten to include ccall in the generated glue JS it substitutes at {{{ SCRIPT }}} in shell.html, which shall then be used whenever the frontend (visual component) wants to communicate with the backend (compiled C++ code).

Emscripten relies on a global module conveniently named Module, onto which ccall and any other glue properties are merged during startup. Additionally, developers can override certain properties of the Module to provide their own behaviour. The only function overridden in the current program is the onRuntimeInitialized, a callback summoned by Emscripten when the WASM runtime is loaded and ready. In this scenario, onRuntimeInitialized calls initGame(), which attaches the necessary event listeners to the game's board. The project's shell file can be found here.

Synergy

Glossary

types.h

These are defined in types.h

  • Square - an alias of unsigned 8 bit integer
  • Bitboard - an alias of unsigned 32 bit integer. The board will be represented by 32 bits despite a typical bitboard being made up of 64. This is because the implementation only cares about the valid squares.
  • SQ_NONE - a sentinel value used to represent invalid/absent squares. There are 32 valid squares on the board, with indices 0-31 (not 1-32 because of zero-based indexing). Therefore 32 is used to represent an invalid square since it's the next value outside this range.
  • Color - an enum used to represent the piece colors (0 for BLACK and 1 for WHITE). The type-specifier-seq is set to uint8_t. Without this, the compiler would pick whatever integer type fits the enumerators (typically an int - 4 bytes). Any place color would have then be stored would take up 4x the space it currently does.
  • Color operator~ - the ~ operator has to be overloaded for the enum Color. This because Color is a scoped enum and without this overload, the compiler would cast the value to an int before applying the bitwise not operator. So ~BLACK becomes ~static_cast<int>(0) which is -1 (0xFFFFFFFF), not 1 and ~WHITE would be -2 (0xFFFFFFFE). Additionally, unscoped enums don't implictly convert from int, so Color opponent = ~side wouldn't compile without an explicit cast (the result is an int and would haveve to be cast to an uint8_t before assigning to Color)
  • PieceKind - an enum used to represent the kind of piece with, 0 representing MAN and 1 representing KING. Its type-specifier-seq is also set to uint8_t so that the piece kind takes up a single byte.
  • Piece - an enum representing the kinds of pieces; 0 for BLACK man, 1 for BLACK king, 2 for WHITE man, 3 for WHITE king and 4 as the sentinel value for empty squares.
  • make_piece function takes in Color and PieceKind and returns the Piece. If 0 is passed in as Color and 0 as PieceKind, 0 << 1 is 0 then ORing the result with PieceKind 0 results in 0, a BLACK man as per the Piece enum. If Color is 0 and the PieceKind is 1, 0 << 1 is 0 then ORing the result with PieceKind 1 gives 1, a BLACK king. When Color is 1 and PieceKind is 0, 1 << 1 is 0010 then ORing the result with PieceKind 0 gives 0010 which is equivalent to 2, a WHITE man according to the Piece enum. Finally, if Color is 1 and PieceKind is 1, 1 << 1 results in 0010, ORing this with the PieceKind 1 gives 0011 which is 3, a WHITE king according to the Piece enum.
  • color_of - returns the color of a piece. It just right shifts the bits by 1, effectively inverting the effect of make_piece. Since make_piece builds a Piece as
    (Color << 1) | PieceKind, the low bit holds PieceKind and the upper bit(s) hold Color. Right-shifting by 1 discards that low PieceKind bit and recovers exactly the Color value that was shifted in. A BLACK man is 0, shifting to the right by 1 gives 0, which corresponds to black in the Color enum. A BLACK king is 0001, shifting to the right by 1 gives 0, black in the Color enum. WHITE man is 0010, right shift by 1 gives 1, which is white in the Color enum. Finally, WHITE king is 0011, right shift by 1 gives 1, which is white in the Color enum.
  • piece_kind - given a Piece, returns the PieceKind (man/king). It masks off the upper bit, since that's where make_piece OR'd in the piece's upper Color bit, leaving only the lower PieceKind bit. BLACK man (0) & 1 returns 0, which corresponds to man in the PieceKind enum. BLACK king (0001) & 1 results in 1, king in the PieceKind enum. WHITE man (0010) & 1 results in man (0 man in the PieceKind enum) and WHITE king (0011) & 1 gives 1, a king according to the PieceKind enum.
  • Move - a struct that holds information about a particular move.
  • The Scores are used by negamax to evaluate a position from the perspective of the side to move (positive scores are good for current player, negative good for opponent). SCORE_WIN/SCORE_LOSS = the side to move has a forced win/loss, where forced means the search has proven the outcome by exhaustively searching all lines to a terminal position within the search tree, not a heuristic estimate. SCORE_DRAW = 0, fires when the game has stalled: either too many moves without a capture/promotion, or the same position recurring (repetition). SCORE_NONE specifically marks an aborted search either due time/node limit hit or stop requested. It tells the caller, "this result isn't trustworthy because the search didn't finish". Finally, SCORE_INF is the initial alpha-beta bound used before any real score has been found.

bitboard.h

Defined here.

  • sq_bb - returns a bitboard with only the specified square populated.
  • rank_bb - returns a bitboard with only the specified rank/row populated.
  • shift_up_right - moves the pieces on a bitboard to the diagonally upright square. For pieces on even rows, this entails left shifting the bits by 4 e.g.
    0x0000000F << 4 = 0x000000F0, the piece that was originally at square 0 is now at square 4, one originally at 1 is now at square 5, one initially at 2 is now at 6 and one that was at 3 is now at 7. For pieces on odd rows, first get rid of the pieces at the furthest right squares since they don't have a valid square to move to. This is achieved by ~RIGHT_EDGE effectively turning all the bits at the right edge off and all the other bits on, then ANDing the result with the odd rows. The result is then finally shifted to the left by 5 bits leading to the pieces moving diagonally up right. For example, the bitboard 0x000000F0 & 0x70707070 = 0x00000070 << 5 = 0x00000E00
  • shift_up_left - moves the pieces to the diagonally up left square. Similar masking logic as shift_up_right happens on the left edges for pieces on even rows as they don't have a valid destination. Then the squares are shifted to the left by 3 to land on the diagonally up left squares. Finally, squares on odd rows are left shifted by 4 with no masking since they'll land on valid squares.
  • shift_down_right - moves the pieces to the diagonally bottom right square. Pieces on odd rows get masked since the pieces at right edge have no valid destination. The result is then right shifted by 3 bits. Pieces on even rows are simply right shifted by 4 since they'll all land on a valid square.
  • shift_down_left - moves the pieces to the diagonally bottom left square. Pieces on odd rows get shifted to the right by 4 bits with no masking as they'll all land on valid squares. Pieces on even rows are masked first since the pieces at the left edge have no valid landing square. Result is then shifted to the right by 5 bits to get final destinations.
  • pop_lsb - gets the index first set bit on a bitboard. For example: bb = 10001100, lowest set bit is at position 2. bb &= bb - 1 clears it: 10001100 & 10001011 = 10001000 and 2 returned.

draw.h

Defined here.

  • is_reversible_draw - since last capture, the number of plies exceed the allowed no-capture threshold. This is an indication of a draw.
  • count_occurrences - counts the number of times the position hash appears in the search history. A position appearing repeatedly indicates a draw.

eval_linear

Defined here and implemented in its cpp companion.

  • extract_features - computes a fixed set of 16 numeric properties of a position (see comments in the header file), always oriented from side_to_move's perspective, and writes them into out[0..15].
  • evaluate - gets the dot product of weights and features to produce the score that helps determine how a player is doing.

eval_material

Defined here and implemented in eval_material.cpp.

  • evaluate - multiplies the difference between between current player's men and opponent's men with a constant value. It then does the same for kings and sums both the scores to get a feel of how the player is doing. It doesn't take into account any factors other than piece counts. It was the initial scoring function used before eval_linear. If interested, you could replace eval_linear with it, just to see how it fairs.
